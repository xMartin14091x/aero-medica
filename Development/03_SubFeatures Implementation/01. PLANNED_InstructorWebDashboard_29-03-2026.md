## Problem Statement

The in-game Dashboard shows only the individual player performance data. Instructors at training institutions (B2B customers) need a centralized view to monitor multiple students simultaneously. Currently there is no mechanism for an instructor to observe student activity without physically looking at their screen. A browser-based instructor dashboard accessible from any device on the same LAN is essential for B2B value.

## Proposed Solution

A 3-component system: (1) lightweight web server (Python FastAPI + SQLite), (2) browser-based instructor dashboard (HTML/JS), (3) Godot game integration via new InstructorReporter autoload.

### Implementation Steps

1. Web Server: FastAPI + SQLite + WebSocket. Endpoints: /api/health, /api/session/start, /api/telemetry, /api/session/end. Package via PyInstaller.
2. Instructor Browser UI: Vanilla HTML/JS. Student list, radar chart, scenario filter, class stats. WebSocket for live updates.
3. Godot InstructorReporter: New autoload. LAN discovery (Ollama-style). POSTs all telemetry events. Local queue with persistent storage (user://pending_telemetry/) when server unreachable -- auto-flushes on reconnect.
4. Settings Integration: Instructor Server section in Settings menu.
5. Packaging: Server as one-click executable.

### API: Game to Server

- GET /api/health -> status ok
- POST /api/session/start -> student_id, student_name, scenario_id, timestamp
- POST /api/telemetry -> student_id, session_id, event_type, data, timestamp
- POST /api/session/end -> student_id, session_id, scenario_id, scores, pass_fail, timestamp

### API: Server to Browser (WebSocket)

- student_connected: student_id, student_name, status
- session_started: student_id, scenario_id
- score_update: student_id, scenario_id, scores, pass_fail
- student_disconnected: student_id

### Database Schema (SQLite)

- students: id TEXT PK, name TEXT, first_seen TEXT, last_seen TEXT
- sessions: id INTEGER PK, student_id TEXT FK, scenario_id TEXT, start_time TEXT, end_time TEXT, scores_json TEXT
- events: id INTEGER PK, session_id INTEGER FK, event_type TEXT, data_json TEXT, timestamp TEXT

## Architecture Decisions

1. Python FastAPI over Go: faster dev, PyInstaller packaging, LAN-scale sufficient. MT approved.
2. SQLite over PostgreSQL: zero install, single file. MT approved.
3. WebSocket for live updates: real-time essential. SSE as fallback. MT approved.
4. LAN-only, no auth for v1: trusted network. Add auth before internet deployment. MT approved.
5. Offline-first preserved: InstructorReporter is additive. No degradation without server.

## Edge Cases / Risks

- Server down mid-session: game continues, ALL telemetry queued to user://pending_telemetry/ as JSON files, auto-flushed chronologically on reconnect, non-blocking
- No network: full offline mode, student not visible to instructor, all data queued locally for eventual sync
- Server down for days: queue accumulates with no size limit, full sync on reconnect
- Duplicate names: UUID-based student_id per install
- Server restart: WebSocket reconnect, SQLite persists
- Large class 50+: pagination if needed
- Firewall: document port 8080 exception

## Resolved Questions (Chief Manager Martin, 29-03-2026)

1. **Student identity:** First-launch name prompt. Player enters name on first game launch, stored in user:// for subsequent sessions.
2. **Web UI theme:** Navy blue -- match the game visual identity.
3. **Telemetry granularity:** Every event. Full telemetry enables instructor to see detailed student actions and enables future replay functionality.
4. **Authentication:** Deferred to a later iteration. v1 is LAN-only, no auth.

## Offline Queue Specification (Chief Manager Martin directive)

When the instructor server is unreachable, the game MUST:
1. Store all telemetry events and session results locally at `user://pending_telemetry/`
2. Each queued payload saved as individual JSON file (timestamp-based filename for ordering)
3. On server reconnect (detected via periodic /api/health probe), auto-flush all queued files in chronological order
4. Successfully transmitted files deleted from local queue after server confirms receipt (HTTP 200/201)
5. Queue has no size limit -- student can play for days offline, all data syncs when reconnected
6. Flush process is non-blocking -- game continues normally while background uploads proceed
