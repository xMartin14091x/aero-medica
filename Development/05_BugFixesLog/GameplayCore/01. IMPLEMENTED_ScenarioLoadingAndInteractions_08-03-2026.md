## Summary

Multiple interconnected bugs prevented all core gameplay from functioning: patients and equipment never spawned, equipment couldn't be picked up, assessments produced no visible results, and the player model was a placeholder capsule in T-pose. This log documents all fixes applied in a single session.

## Bug 1: Patients and Equipment Never Spawn

**Symptom:** Entering any level showed only the environment — no patients, no equipment, no hazards.

**Root Cause:** The UI (`main_menu.gd` and `scenario_select.gd`) called `GameManager.change_scene()` directly to load levels. This only loaded the `.tscn` scene file. Nobody ever called `ScenarioManager.load_scenario()`, which is the function that reads the scenario JSON, spawns patients from `PatientBase.tscn`, spawns equipment, creates hazard systems, and sets up random events.

Additionally, all 5 scenario JSON files had incorrect `environment_scene_path` values — 4 pointed to a deleted `TestLevel.tscn` and 1 pointed to the wrong directory.

**Fix:**
- `main_menu.gd` — Tutorial button now calls `ScenarioManager.load_scenario("res://data/scenarios/scenario_tutorial.json")` instead of `GameManager.change_scene()`
- `scenario_select.gd` — Replaced `scene_path` with `scenario_json` in the SCENARIOS array. `_on_start_pressed()` now calls `ScenarioManager.load_scenario()` instead of `GameManager.change_scene()`
- All 5 scenario JSONs updated with correct `environment_scene_path`:
  - `scenario_tutorial.json` → `res://scenes/gameplay/Tutorial.tscn`
  - `scenario_rta.json` → `res://scenes/gameplay/RoadTrafficAccident.tscn`
  - `scenario_cardiac.json` → `res://scenes/gameplay/CardiacArrest.tscn`
  - `scenario_mci.json` → `res://scenes/gameplay/MassCasualty.tscn`
  - `scenario_fire.json` → `res://scenes/gameplay/BuildingFire.tscn`

**Files Modified:**

## Bug 2: ScenarioManager Null Scene Root Crash

**Symptom:** `Cannot call method 'add_child' on a null value` in `scenario_manager.gd` when loading a scenario.

**Root Cause:** `ScenarioManager.load_scenario()` called `GameManager.change_scene()` which uses `call_deferred("change_scene_to_file")`. The code then did `await get_tree().tree_changed` + `await get_tree().process_frame`, but `current_scene` was still null because the deferred scene change hadn't completed.

**Fix:** Changed to call `get_tree().change_scene_to_file()` directly (not through GameManager's deferred wrapper), then loop-wait until `current_scene` is no longer null, then wait one more frame for `_ready()` to complete on all nodes.

```gdscript
get_tree().change_scene_to_file(env_path)
await get_tree().tree_changed
while get_tree().current_scene == null:
    await get_tree().process_frame
await get_tree().process_frame
```

**Files Modified:**
- `scripts/core/scenario_manager.gd`

## Bug 3: Equipment Cannot Be Picked Up (Property Name Mismatch)

**Symptom:** Walking up to equipment and pressing E did nothing. Equipment was never recognized as equipment.

**Root Cause:** `equipment_entity.gd` exported the property as `data`, but `interaction_manager.gd` (`_is_equipment_entity()`) and `inventory_component.gd` (`_get_equipment_data()`) both searched for a property named `equipment_data`. Since the names didn't match, `"equipment_data" in entity` always returned false.

**Fix:**
- `equipment_entity.gd` — Renamed `@export var data` to `@export var equipment_data`. Added `get_equipment_data()` method for the `has_method()` lookup path.
- `scenario_manager.gd` — Updated `_spawn_entities()` to use `equip.equipment_data` instead of `equip.data`. Also added `equipment_type` enum mapping from JSON string to `EquipmentData.EquipmentType` enum (was previously not set).

**Files Modified:**
- `scripts/gameplay/equipment_entity.gd`
- `scripts/core/scenario_manager.gd`

## Bug 4: Crash on Equipment Pickup (Null current_target)

**Symptom:** `Invalid access to property or key 'name' on a base object of type 'Nil'` when picking up equipment.

**Root Cause:** `InventoryComponent.try_pickup()` reparents the equipment node from the scene to `HeldItemMount`. This reparenting causes the equipment to leave the `InteractionArea`, triggering `body_exited`, which sets `current_target = null`. Then `_log_interact()` on the next line tries to access `current_target.name` — crash.

**Fix:** Capture the target name before calling `try_pickup()`, then use a null-safe `_log_interact_named()` method. Also added a null guard to the original `_log_interact()`.

```gdscript
# Before pickup — capture name while target is still valid
var target_name := current_target.name
_inventory.try_pickup(current_target)
_log_interact_named(interactable, target_name)
```

**Files Modified:**
- `scripts/gameplay/interaction_manager.gd`

## Bug 5: Player Model T-Pose and Root Motion Drift

**Symptom:** Player was a capsule placeholder. After applying the doctor.glb model, it showed in T-pose. After adding animation playback, the walking animation's root motion caused the character to visually drift forward, then snap back to its actual position when the animation looped.

**Root Cause:** The Mixamo walking animation includes position keyframes on the root bone (Hips) that translate the skeleton forward over time. The game also moves the `CharacterBody3D` via velocity — double movement. The visual position drifted ahead of the physics position, then snapped back on animation loop.

**Fix (and why it works):**

The fix strips root motion at the Animation resource level. On startup, `_strip_root_motion_from_all()` iterates every animation in the AnimationPlayer's library and **removes** any `TYPE_POSITION_3D` tracks that target the root bone (Hips). This is done once at `_ready()` time by modifying the in-memory Animation resources.

```gdscript
func _strip_root_motion_from_all(root_bone_name: String) -> void:
    var anim_lib := _anim_player.get_animation_library("")
    for anim_name in anim_lib.get_animation_list():
        var anim := anim_lib.get_animation(anim_name)
        for track_idx in range(anim.get_track_count() - 1, -1, -1):
            var path := anim.track_get_path(track_idx)
            if root_bone_name in str(path) and anim.track_get_type(track_idx) == Animation.TYPE_POSITION_3D:
                anim.remove_track(track_idx)
```

**Why previous approaches failed:**
1. `model.position = Vector3.ZERO` — Only locks the parent Node3D, but the Skeleton3D inside still translates via bone poses.
2. `skeleton.set_bone_pose_position()` per frame — The AnimationPlayer processes AFTER `_physics_process`, overriding bone poses we set.
3. Removing tracks from the Animation resource — Works because the AnimationPlayer has no position data to apply. The rotation and scale tracks remain, so legs/arms/body still animate naturally. Only the forward translation is removed.

**Additional features added:**
- Auto-detect idle/walk animations by name from GLB
- Model rotates smoothly to face movement direction
- Switches between idle and walking animations based on input

**Files Modified:**
- `scenes/entities/player/Player.tscn` — Replaced CapsuleMesh with `doctor.glb` PackedScene instance
- `scripts/gameplay/player_controller.gd` — Animation system, root motion stripping, model rotation

## Technical Debt Assessment

### Is root motion stripping technical debt?

**No — this is the correct solution.** Root motion stripping at the Animation resource level is the standard approach in game engines when you want animations to play in-place while a separate system (CharacterBody3D velocity) handles actual movement. This is not a workaround — it's how Mixamo animations are meant to be used in games with physics-driven movement.

The alternative (re-exporting the GLB from Mixamo with "In Place" checked) would avoid the runtime stripping, but would require re-downloading every animation. The runtime approach is equally valid and more flexible — it works with any animation source automatically.

### Actual technical debt items from this session

These items are documented in `07_TechnicalDebt/`:

1. **Assessment results have no visual feedback** — The assessment system works (data is computed, stored on patient metadata, logged to telemetry), but no UI shows the player what they assessed (e.g., "Airway: CLEAR", "Pulse: Present"). The ActionMenu opens, the player selects an assessment, but sees no result.

2. **SyncThing deletes binary assets** — The `doctor.glb` and texture files were wiped by SyncThing. The `.stignore` should be configured to protect binary assets, or `.godot/` and large binaries should be excluded from sync.

3. **Print statements in player_controller.gd** — Debug `print()` calls for animation names and root bone info should be removed before release.
